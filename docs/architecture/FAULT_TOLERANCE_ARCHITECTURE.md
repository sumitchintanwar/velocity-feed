# Production-Grade Fault Tolerance Architecture

**Status:** Proposed  
**Author:** Staff Distributed Systems Engineer  
**Component:** Gateway Cluster & Client SDK  

## 1. Executive Summary
As the RTMDS scales to serve millions of events per second across thousands of geographically distributed clients, failure is not an anomaly—it is a continuous operational state. 
This document outlines the design for our fault-tolerance layer, ensuring that the system can survive Gateway crashes, client network partitions, and cascading failures with zero data loss and automated recovery.

---

## 2. Architecture Overview
Fault tolerance in RTMDS spans three primary domains:
1. **The Edge (Client <-> Gateway):** TCP/WebSocket layer resiliency, silent disconnect detection, and stateful session resumption.
2. **The Node (Gateway Lifecycle):** Graceful shutdown, connection draining, and load balancer integration.
3. **The Cluster (Gateway <-> Broker):** Backpressure handling and automatic client shedding to prevent memory exhaustion.

---

## 3. Heartbeat Protocol

Relying solely on TCP KeepAlive is insufficient for detecting application-level lockups or half-open NAT connections. We introduce a bidirectional, application-level heartbeat over the WebSocket protocol.

### 3.1 Design
- **Gateway-to-Client `ping`:** The Gateway emits a lightweight `{"type": "ping", "ts": 1718302000}` frame every `15s`.
- **Client-to-Gateway `pong`:** The client must respond with a `pong` frame within `5s`.
- **Timeout Semantics:** If the Gateway misses two consecutive `pongs` from a client, the Gateway forcibly terminates the TCP connection to reclaim file descriptors and memory.
- **Client-Side Timeout:** If the client receives no `ping` (or any market data) from the Gateway for `30s`, it assumes a silent network partition, drops the connection locally, and initiates the reconnect flow.

### 3.2 APIs
*JSON Format (also mapped to binary Protobuf/FlatBuffers envelopes):*
```json
// Gateway -> Client
{ "type": "ping", "timestamp": 1718302000 }

// Client -> Gateway
{ "type": "pong", "timestamp": 1718302000 }
```

## 4. Reconnect Flow & Stream Resumption

When a network partition resolves or a Gateway crashes, clients will experience a disconnect. To guarantee **zero data loss**, clients must be able to resume streams exactly where they left off without receiving duplicates.

### 4.1 Sequence Tracking
Every market event (`Quote`, `Bar`) generated by the `Sequencer` includes a strictly monotonic `seq` (sequence number) per symbol. The Client SDK must track the highest `seq` received for each active subscription.

### 4.2 Reconnection Protocol (GoAway & Resume)
When the Client SDK detects a disconnect, it triggers an Exponential Backoff reconnect loop with Jitter to prevent thundering-herd attacks on the remaining Gateways.

Once a new WebSocket connection is established, the client issues a stateful subscribe request:
```json
{
  "action": "subscribe",
  "symbols": ["AAPL", "TSLA"],
  "resume_seq": {
    "AAPL": 10543,
    "TSLA": 9901
  }
}
```

### 4.3 Gateway Replay
Upon receiving a `resume_seq`, the Gateway queries the `WAL/Replayer` for events occurring *after* that sequence. 
1. Gateway fetches missed events (`10544` to current for AAPL).
2. Gateway streams missed events to the client.
3. Gateway stitches the client back onto the live `TopicManager` broadcast channel seamlessly.

## 5. Gateway Health Monitoring

Load balancers (e.g., Nginx, HAProxy, AWS ALB) require deterministic endpoints to route traffic away from failing nodes.

### 5.1 Endpoints
- **`/healthz` (Liveness):** Returns `200 OK` if the HTTP server is responsive and goroutines are not deadlocked. If this fails, Kubernetes will `SIGKILL` the pod.
- **`/readyz` (Readiness):** Returns `200 OK` only if the Gateway is successfully connected to upstream services (e.g., Kafka/Sequencer). If this fails, the load balancer removes the node from the rotation, but existing clients are not killed immediately.

---

## 6. Gateway Lifecycle & Graceful Shutdown (Draining)

During deployments or scale-down events, Gateways must shut down without abruptly severing connections.

### 6.1 Draining Flow
1. **SIGTERM Received:** Kubernetes/OS sends a `SIGTERM` to the Gateway.
2. **Readiness Flipped:** The Gateway immediately marks `/readyz` as `503 Service Unavailable`. Load balancers stop routing *new* connections to this node.
3. **GoAway Broadcast:** The Gateway broadcasts a `{"type": "goaway", "reason": "server_shutdown"}` control message to all active clients.
4. **Client Handoff:** Upon receiving `goaway`, the Client SDK actively initiates a reconnect to the load balancer (which will route it to a healthy, `/readyz`-passing node).
5. **Connection Bleed:** The Gateway waits up to `30s` for all clients to disconnect voluntarily.
6. **Hard Shutdown:** After the timeout, any remaining connections are forcibly closed and the process exits.

## 7. Failure Scenarios & Mitigations

| Failure Mode | Detection Mechanism | Mitigation Strategy |
| :--- | :--- | :--- |
| **Silent Client Partition** | Missed `pong` heartbeat | Gateway forcefully closes socket, reclaims RAM. |
| **Gateway Crash (OOM/Panic)** | Client stops receiving bytes | Client TCP EOF or `ping` timeout; triggers SDK reconnect with `resume_seq`. |
| **Thundering Herd Reconnect** | Cluster-wide connection spike | SDK uses Exponential Backoff + 20% Jitter. Gateway enforces a max `Accept()` rate limit. |
| **Slow Client (Backpressure)**| Gateway socket buffer fills | Client Queue ring-buffer drops oldest messages. Client receives `{"type": "error", "msg": "slow_client"}`. |

## 8. Failure Metrics (Observability)

To monitor fault tolerance, the following Prometheus instruments must be added:
- `rtmds_client_disconnects_total{reason="heartbeat_timeout|eof|slow_client"}`: Counter
- `rtmds_gateway_draining_active`: Gauge (1 if shutting down, 0 otherwise)
- `rtmds_client_reconnect_latency_seconds`: Histogram (Time from disconnect to successful resume)
- `rtmds_replay_events_served_total`: Counter (Number of historical events fetched during reconnects)

## 9. Chaos Testing Plan

To validate this design in CI/CD, we will implement a suite using tools like `Toxiproxy` or Kubernetes Chaos Mesh:
1. **The Blackhole:** Use `iptables` to drop packets between Gateway and Client. Verify that both sides time out via Heartbeats within 30s.
2. **The Guillotine:** Send `SIGKILL` to a Gateway serving 10,000 clients. Verify the cluster absorbs the reconnect storm without OOMing, and no data is lost (validated via sequence gaps).
3. **The Slowpoke:** Artificially limit a client's TCP receive window to 1 byte/sec. Verify the Gateway detects backpressure, drops the client, and does not degrade performance for healthy clients.

---

## Conclusion
This architecture transforms the RTMDS Gateway from a fragile, stateful socket server into an ephemeral, stateless edge node. By pushing sequence state to the edge (Client SDK) and introducing strict lifecycle management (Draining & Heartbeats), the cluster can gracefully handle arbitrary failures at immense scale.
